# Reconcile local Codex Skill discovery

## Mission

Apply and verify the repository's new Skill source/discovery contract on the User's
actual machine without redesigning it, deleting legacy source material, or mutating
project runtimes.

## Why Codex is required

This work requires machine-local filesystem state and Codex CLI behavior unavailable
to ChatGPT: `~/.codex/AGENTS.md`, `$HOME/.agents/skills`, legacy local Skill folders,
`/Users/wenv/Documents/skills/LOCAL_SKILLS.md`, symlink creation/inspection, and a
fresh local Codex discovery smoke test.

## Current evidence / diagnosed problem

OpenAI's current Codex Skill documentation defines local discovery under
repository/user/admin `.agents/skills` locations and explicitly supports symlinked
Skill folders. It recommends plugins for reusable external distribution.

The previous local policy used legacy `~/.codex/skills/` semantics and prohibited
first-party discovery symlinks. The repository policy has now been corrected; the
machine-local state must be reconciled to match it.

## Required changes

### A. Machine-wide `~/.codex/AGENTS.md`

Make the smallest edits needed so it states the following current contract:

```text
FIRST_PARTY maintained source:
/Users/wenv/Documents/skills/<name>/

Codex user-scoped discovery:
$HOME/.agents/skills/<name>
→ normally symlink to maintained first-party source

Codex repository-scoped discovery:
$REPO_ROOT/.agents/skills/<name>

Third-party reusable distribution:
prefer supported plugin when appropriate; otherwise expose upstream Skill through a
current .agents/skills discovery path without converting ownership
```

Remove/replace any active rule that treats `~/.codex/skills/` as the canonical
current discovery location or prohibits first-party discovery symlinks.

Do not duplicate the full `agent-collaboration` protocol into machine-wide AGENTS.

### B. First-party discovery exposure

Use `/Users/wenv/Documents/skills/LOCAL_SKILLS.md` plus actual source folders as the
inventory. For each active standalone FIRST_PARTY Skill that has a valid root
`SKILL.md` and is intended for user-wide Codex use:

```text
$HOME/.agents/skills/<skill-name>
→ symlink → /Users/wenv/Documents/skills/<skill-name>
```

Rules:

- create `$HOME/.agents/skills` if absent;
- inspect every target before mutation;
- if the desired symlink already exists and resolves correctly, keep it;
- if a conflicting file/directory/symlink exists, do not overwrite it; record the
  conflict and leave that Skill unresolved;
- do not create duplicate copies of first-party source;
- do not modify the first-party Skill source repositories in this task.

### C. Third-party discovery exposure

Inspect third-party Skills actually used by the machine.

Precedence:

1. If an installed supported plugin already provides the Skill, prefer that plugin
   and do not create a duplicate user-scoped discovery entry.
2. Otherwise, if the Skill currently exists only as upstream/direct source under a
   legacy location, expose the existing upstream Skill folder through a symlink under
   `$HOME/.agents/skills/<name>` when there is no conflict.
3. Preserve existing third-party source and ownership. Do not mirror it into a
   first-party repository.
4. Do not delete `~/.codex/skills/` or `~/.codex/upstream/` in this task; legacy
   locations may remain as source/rollback material but are no longer the policy
   authority.

If a Skill name is ambiguous between plugin/direct/user-scoped sources, do not invent
precedence beyond the rules above; record the conflict.

### D. `LOCAL_SKILLS.md`

Preserve its existing ownership/source information. If its current schema can accept
this without redesign, update first-party entries to record the actual Codex discovery
exposure under `$HOME/.agents/skills/<name>`. If doing so would require redesigning
the inventory format, leave it unchanged and document that limitation instead.
